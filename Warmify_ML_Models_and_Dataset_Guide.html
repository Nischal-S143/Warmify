Warmify — Executive Technical Summary & ML Formulation

ML Overview
The Core Problem & ML Value Proposition

AWS Lambda cold starts delay user requests by 2,000 ms to 5,000 ms. Native AWS scaling is purely reactive—it only scales after CloudWatch alarms fire (2–3 minutes late), exposing real users to severe latency.

Warmify is proactive: It runs an automated 1-minute closed loop that forecasts incoming traffic 10 minutes into the future using Quantile Gradient Boosting Regression and dimensions provisioned containers via Little's Law, eliminating 98.4% of cold starts.

📌 The 4 Pillars of the Warmify Solution

1. Quantile Time-Series Forecasting

Gradient Boosting Regressors trained with Pinball Loss ($lpha = 0.90$) intentionally over-predict by design to shield against 90% of sudden bursty traffic peaks.

2. Operational Queuing Theory (Little's Law)

Translates forecasted request velocity into exact required microVM concurrency: Copies = ceil(RPS × Service_Time × 1.5).

3. Autonomous Safety Guardrails Envelope

Guarantees stability through min floor clamp (MIN=1), max budget cap (MAX=50), dead-band anti-flapping (±2), and gradual scale-down dampening.

4. Lightweight Serverless Execution

Model runs in <15 ms on Lambda CPU with a tiny 120 KB artifact footprint, avoiding heavy framework cold starts inside the controller itself.

The Machine Learning Model: Quantile Gradient Boosting

Algorithm Deep Dive

Algorithm: GradientBoostingRegressor with Quantile Loss

Warmify employs tree-based Gradient Boosting Regressors (from scikit-learn.ensemble). It constructs an ensemble of shallow decision trees iteratively, where each successive tree minimizes the Quantile / Pinball Loss function.

⚙️ Model Hyperparameters & Tuning Architecture

Hyperparameter Tuned Value Engineering Justification
loss "quantile" Asymmetrical loss function optimizing for coverage rather than conditional mean.
alpha ($lpha$) 0.50, 0.90, 0.95 Quantiles targeting median cost efficiency, balanced protection, and mission-critical SLAs.
n_estimators 200 200 sequential boosting stages ensure optimal convergence across diurnal ramps.
max_depth 5 Prevents overfitting while modeling complex non-linear lag interactions.
learning_rate 0.05 Small shrinkage parameter guarantees stable gradient steps and prevents variance spikes.
subsample 0.8 Stochastic sampling: trains each tree on 80% random sub-samples to reduce tree correlation.

📐 Pinball / Quantile Loss: Why Mean Squared Error (MSE) Fails

Standard MSE models predict the average traffic. In auto-scaling, 50% of incoming bursts will exceed the average, triggering massive cold starts! Pinball loss asymmetrically penalizes errors:

$$L_lpha(y, \hat{y}) = egin{cases} lpha (y - \hat{y}) & ext{if } y \ge \hat{y} \quad ext{(Under-prediction penalty: cold start danger)} \ (1 - lpha)(\hat{y} - y) & ext{if } y < \hat{y} \quad ext{(Over-prediction penalty: harmless mild buffer)} \end{cases}$$

model_q50.pkl ($lpha=0.50$)

Median Forecast: Symmetric penalties. Best for steady, predictable workloads prioritizing minimum cloud spend.

model_q90.pkl ($lpha=0.90$)

Default Model: Under-predicting penalized 9× more. Pre-warms 90% of peaks with <48ms P95 latency.

model_q95.pkl ($lpha=0.95$)

Mission-Critical: Under-predicting penalized 19× more. 100% cold start elimination for payments/checkout.

Why Gradient Boosting Over Deep Learning (LSTM / Transformers)?

Lambda Runtime Reality: Scikit-learn evaluates in < 15 ms with a 120 KB model. Deep learning (PyTorch/TensorFlow) requires 400 MB+ dependencies and 800 ms initialization—which would cause a cold start inside the auto-scaling engine itself! Furthermore, empirical benchmarks consistently prove tree boosting matches or beats LSTMs on engineered tabular features.

🔄 Deep Dive: Why Sine and Cosine for Time-of-Day?

The Integer Time Discontinuity Problem

If time is represented as an integer (0 to 23 hours), 23:59 and 00:01 appear mathematically as far apart as possible: $|23.98 - 0.01| = 23.97$ units apart! A decision tree splits them into opposite branches, completely losing the fact that they are just 2 minutes apart.

The 2D Unit Circle Solution

By projecting minute $M$ onto the unit circle via $(\sin, \cos)$, 23:59 and 00:01 have a Euclidean distance of $< 0.008$. Furthermore, combining both $\sin$ and $\cos$ ensures 06:00 AM and 06:00 PM are never confused (since $\cos$ differentiates them).

# Exact cyclical time transformation in lambdas/controller/app.py: minutes_of_day = dt.hour * 60 + dt.minute sin_time = math.sin(2 * math.pi * minutes_of_day / 1440) cos_time = math.cos(2 * math.pi * minutes_of_day / 1440)

Why Forecast 10 Minutes Ahead ($\Delta t = 10$) Instead of 1 Minute?

AWS Provisioned Concurrency takes 60 to 180 seconds to initialize new microVM execution environments in AWS data centers. Predicting $t+1$ minute would arrive too late; containers would still be booting. A 10-minute horizon ensures full pre-warming before the traffic arrives.

The Dataset: Kaha Se Aaya? (Origins & Architecture)

Dataset Origin
Answering the Viva Question: "Where did your dataset come from?"

Warmify operates on real-time serverless telemetry. It does not use a static Kaggle CSV. Instead, Warmify utilizes a three-tier dataset architecture: CloudWatch live production ingestion, a realistic Circadian Load Generator, and a local simulated telemetry store.

🌐 The 3 Dataset Sources in Warmify

Source 1: AWS Production Telemetry Ingestion (Deployed Cloud Mode)

🚫 Critical Time-Series Rule: Why shuffle=False

In time-series forecasting, standard random cross-validation or shuffling causes Temporal Data Leakage (training on future samples to predict past samples). Warmify enforces a strict 80/20 chronological split where the model trains on the first 80% of historical time and evaluates strictly on the unseen subsequent 20%.

Little's Law Queuing Theory & Safety Guardrails

System Actuation

The Bridge from ML Predictions to Serverless Infrastructure

Machine learning outputs forecasted request volume ($\hat{y}_{Q90}$ in requests per minute). However, AWS Lambda does not scale by requests—it scales by concurrent microVM execution units. Warmify applies Little's Law from operational queuing theory to bridge this gap.

📐 Little's Law Dimensioning Formula

$$L = \lambda imes W$$ $$ ext{Raw Copies} = \left\lceil \left( rac{\hat{y}_{Q90}}{60} ight) imes \left( rac{ar{d}_{ ext{duration\_ms}}}{1000} ight) imes 1.5 ext{ (Headroom)} ight ceil$$

$\lambda$ (Arrival Rate)

Forecasted requests/min converted to requests per second: $\lambda = \hat{y}/60$.

$W$ (Service Time)

Average execution duration of the target function in seconds: $ar{d}/1000$.

$1.5 imes$ Safety Headroom

Absorbs intra-minute micro-bursts and sub-second Poisson variance.

🛡️ The 4 Safety Guardrails (The Protective Envelope)

Raw ML outputs never touch cloud infrastructure directly without passing through strict safety bounds:

1. Minimum Floor Clamp (MIN_PC = 1) Baseline Health

Never scale to 0. Keeping 1 warm copy guarantees instantaneous response for health checks at trivial cost ($0.003/day).

2. Maximum Budget Cap (MAX_PC = 50) Cost / DDoS Shield

Hard ceiling protecting the AWS billing account against runaway loops, traffic anomalies, or DDoS attacks.

3. Dead-Band Hysteresis (DEAD_BAND = 2) Anti-Flapping

If $| ext{target} - ext{current}| \le 2$, do nothing. Prevents AWS Provisioned Concurrency thrashing on minor fluctuations.

4. Gradual Asymmetric Scale-Down (STEP = 1) Latency Defense

Warmify scales UP instantly to prevent cold starts, but scales DOWN conservatively (1 unit/min) so containers aren't prematurely dropped during brief pauses.

📊 Key Findings & Comparative Insights

Why Ping Warmers Fail (12.4% Cold Starts)

A periodic ping only keeps 1 single container alive. When 10 users hit the function concurrently, 1 user gets a fast response while 9 suffer severe 2,000ms+ cold starts. Pings cannot solve concurrency spikes.

Why AWS Auto-Scaling Fails (7.2% Cold Starts)

AWS Target Tracking relies on CloudWatch metric aggregations and alarms. The 3-minute lag means containers are provisioned after the burst has already caused cold starts for real users.

🏆 The Warmify Advantage: 48 ms P95 Latency for Just 1 Cent More

Warmify Q90 slashed cold starts from 18.6% down to 0.3%, reducing P95 latency from 2,480 ms to 48 ms (a 51x speedup). The cost difference over reactive auto-scaling was only $0.0109 for 2 hours—a virtually free upgrade for production SLAs.

Bulletproof answers to the most common questions professors, evaluators, and system architects will ask during your presentation:

Q1: "Which ML algorithm did you use, and why not an LSTM or Deep Neural Network?"

Scikit-learn runs in <15 ms with a 120 KB footprint and natively supports Quantile Pinball Loss."
Q2: "What is Quantile Regression and why not use Mean Squared Error (MSE)?"
Answer: "MSE predicts the conditional average. If we scale serverless containers based on average load, 50% of traffic peaks will exceed capacity, triggering cold starts! Quantile regression with Pinball Loss penalizes under-prediction 9× more heavily than over-prediction (at $lpha=0.90$), intentionally creating an asymmetric buffer that pre-warms containers for 90% of traffic peaks."
Q3: "Where did your dataset come from? Is it real or synthetic?"
Answer: "Warmify supports two authentic modes: In cloud production, telemetry is pulled live from AWS CloudWatch Metrics & Logs Insights by our Collector Lambda. For controlled lab experiments, we engineered a Circadian Synthetic Load Generator modeling real 24-hour diurnal enterprise traffic with ±15% stochastic Gaussian jitter. We also include a pre-seeded local JSON dataset for offline demos."
Q4: "Why use Sine and Cosine cyclical encodings for time-of-day?"
Answer: "Time is continuous and circular. If represented as an integer 0–23, 23:59 and 00:01 appear as opposites ($|23.98 - 0.01| = 23.97$), confusing tree models. Projecting minutes onto the 2D unit circle via $\sin$ and $\cos$ ensures 23:59 and 00:01 remain adjacent (distance < 0.008) across midnight."
Q5: "How do you translate forecasted requests into actual Lambda instances?"
Answer: "We use Little's Law from operational queuing theory: $L = \lambda \cdot W$. We convert predicted requests per minute into arrival rate ($ ext{req/sec}$), multiply by average service execution duration (seconds), and apply a $1.5 imes$ safety headroom: $ ext{Copies} = \lceil ext{RPS} imes ext{Duration} imes 1.5 ceil$."
Q6: "What if traffic surges far beyond your ML model's prediction?"
Answer: "Warmify has built-in safety fallbacks: 1) Standard AWS on-demand concurrency serves excess traffic without request drops; 2) The controller loops every 60 seconds to rapidly recalibrate; 3) A budget cap (50 copies) protects against DDoS bill shock."
